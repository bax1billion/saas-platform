# Brand Strategy Playbook

A reusable framework for naming, positioning, and voicing a new SaaS product. Apply it to any product launched on this platform.

---

## 1. Brand Architecture

Separate three layers and decide each deliberately:

| Layer | What it is | Where it appears |
|---|---|---|
| **Product name** | The brand customers see and say | Site, UI, conversations, marketing — branding everywhere |
| **Company name** | The legal/umbrella entity | Legal docs, copyright line, footer, invoices |
| **Domain** | The practical address | URL, email addresses |

The product name and company name may differ, and the domain often follows the company (or a longer variant of the product name) because short product-name domains are rarely available.

**Why this model works:**

1. **Separates brand from infrastructure** — the product name can be emotional and memorable; the domain just needs to be practical and available.
2. **Avoids death by comparison** — an evocative product name doesn't slot into an existing category label ("X system", "X software"), so it feels different immediately.
3. **Aligns with positioning** — pick name components that literally encode the brand values you want to project.
4. **Flexibility to expand** — the company umbrella can ship more products later without renaming anything.

### Brand application map

Decide, before launch, exactly which name appears where:

| Surface | Rule |
|---|---|
| Navigation / logo | Product name only (distinct logotype treatment) |
| Hero | Product name + tagline + one-line positioning statement |
| Footer / legal | `© <year> <Company name>` |
| About page | "<Product> is built by <Company>." |
| SEO title tag | `<Product> \| <two-to-three-word category descriptor>` |
| Meta description | ICP + top 2–3 verbs/outcomes in one sentence |
| Target keywords | Product name variants + category keywords + ICP keywords |

## 2. Naming Methodology

### Principles (research-backed)

A strong SaaS name is:

- **Memorable** — evocative beats descriptive in a crowded category.
- **Simple** — easy to spell and pronounce. 77% of consumers say hard-to-spell names reduce credibility. If a longer/foreign root is used anyway, plan pronunciation guides in marketing material.
- **Mission-relevant** — 72% of consumers say mission-aligned names create trust. The name should encode the product's core value (e.g., trust, speed, clarity), not just its category.
- **Unique** — avoid crowded generic terms and purely descriptive names in crowded categories; they invite direct comparison with incumbents.
- **Scalable** — must not box the product into one feature or one vertical if expansion is plausible.
- **Securable** — matching .com domain and social handles must be available. Failing to secure a matching domain harms brand recognition.

### Generation technique: meaningful root + modern descriptor

1. List the **core values/emotions** the product must evoke (trust, protection, clarity, speed…).
2. Find **root words that literally mean those values** — Latin/Greek roots work well because they sound distinctive and professional while carrying real meaning (e.g., *veritas* = truth, *fides* = trust, *custodia* = protection, *integritas* = wholeness).
3. Combine each root with a **modern SaaS descriptor suffix**: Core, HQ, App, Docs, Works, Comply, CX, Records… The root carries emotion; the suffix signals what kind of thing it is.
4. Also consider **portmanteau and metaphorical names** — they intrigue, but can confuse; test them.

### Candidate evaluation table

Build a table for every candidate:

| Column | Content |
|---|---|
| Candidate name | — |
| Meaning & rationale | What the roots mean; what the combination signals |
| Domain availability | Checked on a specific, recorded date |
| Branding notes | Pronounceability, connotations, comparison risk, expansion room |

### Decision rules

1. **Align with mission and emotional appeal** — prefer names whose roots literally invoke the product's core promise.
2. **Balance descriptiveness and uniqueness** — a descriptive cue (what it is) plus an evocative element (why it's different) avoids both genericness and obscurity. A category acronym in the name (e.g., "…QMS") aids comprehension but invites comparison with enterprise incumbents — trade off consciously.
3. **Prefer easy pronunciation and spelling**; shortlist short names.
4. **Secure the .com and social handles before finalizing.** Record the date availability was checked.
5. **Test the shortlist with the target audience** — quick surveys or informal tests with people matching the ICP. Perceptions vary; don't decide on internal taste alone.
6. **Document the final decision** — name, meaning, why it won, and confirmation the domain was secured.

> **Example (from a compliance-SaaS launch):** "Veritas" (Latin: truth) + "Core" (central system of record) + "Works" (functional workspace) → product "Veritas Core", company/domain "VeritasCoreWorks / veritascoreworks.com". Chosen because it encoded the core promise (verifiable truth), avoided comparison with enterprise QMS suites, and the .com was available.

## 3. Positioning Framework

Define each of these, in writing, before building the marketing site:

1. **Positioning statement** — one sentence: *"<Product> is the <role/metaphor> for <specific ICP>."* Use a role metaphor ("co-pilot", "workspace", "system of record") rather than a category label.
2. **Core promise** — one quoted sentence stating the outcome the customer can rely on (e.g., *"Always <desired state>, with <proof/mechanism>."*).
3. **Golden Circle (Sinek):**
   - **Why:** the belief — what the customer deserves.
   - **How:** the mechanism — the single workspace/loop that delivers it.
   - **What:** "<Product> — the <category descriptor> for <ICP>."
4. **Value proposition pillars** — 3–5 pillars, each a noun phrase + one supporting sentence. A durable pattern for SMB SaaS:
   - **Trust/reliability** — why the customer can depend on the records/outputs.
   - **Simplicity & speed** — onboard in days, not months; no endless configuration or hidden modules.
   - **Visibility & control** — status at a glance; know what's current and what's at risk.
   - **Affordability** — transparent pricing, no per-seat surprises.
5. **Competitive differentiation table** — for each named competitor: their focus, and one line on *why you win* (too complex/expensive for the segment, overkill features, pricing model that deters small teams…). The pattern: incumbents overserve the enterprise; you win the underserved segment with focus, simplicity, and transparent pricing.
6. **Tagline set** — write several and map each to a context rather than forcing one everywhere:

   | Tagline slot | Use |
   |---|---|
   | Brand statement | Hero, top of deck |
   | Product positioning | Category pages, listings |
   | Short/punchy | Ads, social |
   | Narrative | Long-form copy, about page |

### Segment-focus rationale (for solo/small founders)

Reusable reasons a small player can win a crowded market — verify each applies before committing:

- **Niche focus:** incumbents chase enterprise; a specific underserved segment is left with spreadsheets and shared drives. Micro-SaaS wins by "solving specific problems," not chasing buzzwords.
- **High pain → high retention:** when failure is expensive for the customer, reliability beats flashy features and churn stays low.
- **Agility and customer intimacy:** iterate fast, answer personally; SMBs prefer a responsive vendor over enterprise bureaucracy.
- **Targeted channels:** niche communities, practitioner groups, consultant blogs, and newsletters beat paid spend — pair with a plain-spoken value proposition ("I built a simple X for people who hate Y").
- **Partnerships and endorsements:** local/industry associations, consultants, and pilot programs traded for testimonials and case studies.
- **Essentials first:** competitors bundle many modules; ship the 3–4 capabilities the buyer actually cares about, robustly, before anything else.

## 4. Voice & Tone

- **Voice:** reassuring, straightforward, professional — "boring but effective." For products bought to reduce risk or anxiety, calm confidence sells; cleverness doesn't.
- **Verb list:** pick 4–6 concrete verbs that define the product's action vocabulary (e.g., track, protect, prove, simplify, verify) and use them everywhere — headlines, feature names, CTAs.
- **Outcomes over features:** phrase benefits as the customer's felt outcome ("sleep well before your next <high-stakes event>"), not capability lists.
- **Speak to anxieties:** name the buyer's recurring worries and show the product "has their back."
- **Avoid:** jargon, AI buzzwords, enterprise-speak, false urgency.
- **Copy formulas that work:**
  - *Pain-point framing:* "<Current tool> can't <prove/deliver the outcome>. <Product> keeps <the important things> in one <adjective> system."
  - *Feature language:* "<Feature name> — <verb> <object> so you always <outcome>."

### Microcopy rules (marketing and in-app)

- **CTAs:** first-person, value-oriented — "Start my <outcome> trial", never "Submit" or "Get Early Access". Be clear about what happens on click; create urgency without false scarcity; address objections inline.
- **Form fields:** explain *why* info is needed, one sentence max ("Used to send your access link").
- **Errors:** neutral, guiding, specific — say what went wrong and what to do next; never blame the user.
- **Trust signals:** short factual statements (data residency, certifications/standards supported, immutability/security claims) repeated consistently across marketing and app.
- **Tone:** calm and clear; friendly means considerate, not jokey.

## 5. Visual Identity Framework

### Color

- Pick **2–3 main colors** plus neutrals; more destroys harmony.
- Choose by psychology, and document the rationale in a table (`Role | Color | Hex | Rationale`): blue → trust/dependability; green → growth/health/positive status; warm accents (amber/red) → attention/urgency — reserve exclusively for warning/critical states, never in marketing copy, to keep the overall tone reassuring; neutral grays → breathing room.
- **Accessibility:** every text/background combination meets **WCAG 4.5:1**; test the primary pairings before shipping.
- Plan **dark mode** from day one using the same psychological principles.
- **Validate the palette with target users** — color perception varies by culture and context.
- Deliberately differentiate the palette from the incumbent look of the vertical.

### Typography

- **Sans-serif body** (e.g., Inter, IBM Plex Sans) for on-screen clarity; **serif headings** (e.g., Merriweather, Libre Baskerville) when authority/credibility is the brand goal. Good typography measurably improves user response (~13%).
- Body ≥ **16px**; line height **1.5×**; adequate letter spacing.
- **2–3 distinct type sizes** to establish hierarchy; light/regular body, semi-bold headings, bold CTAs.
- No decorative or script fonts outside the logo.

### Imagery & iconography

- **Photos:** real environments of the ICP's world; desaturated with a brand-color overlay so content stays the focus.
- **Icons:** simple line icons for the core objects/actions; accent colors; match UI corner radius.
- **Patterns:** abstract geometric patterns (suggesting the product's data/flow) for hero backgrounds.

## 6. Email Domain Architecture

Isolate email reputation by purpose with three subdomains:

| Subdomain | Purpose | Example senders |
|---|---|---|
| `marketing.<domain>` | Newsletters, announcements, waitlist | `hello@marketing.<domain>` |
| `alerts.<domain>` | App transactional (action required, exports, reminders) | `noreply@alerts.<domain>` |
| `auth.<domain>` | Auth mail (verification codes, password resets, MFA) | `noreply@auth.<domain>` |

**Why:** marketing mail draws the highest spam-complaint rates; isolating it protects transactional and auth deliverability. If `marketing.` reputation dips, `alerts.` and `auth.` are unaffected.

**Setup checklist (per new product):**

- [ ] Verify all three subdomains with the email provider
- [ ] Set DKIM, SPF, and DMARC records for each
- [ ] Point the auth provider's mailer at the verified `auth.` sender (built-in mailers usually have tiny daily limits — e.g., Cognito's is 50/day until SES-backed)
- [ ] Request production sending access (out of sandbox) for each domain
- [ ] Define the canonical FROM address per purpose and use it consistently
